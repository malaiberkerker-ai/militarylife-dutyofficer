# 連值星官的一天｜遊戲工程規格書

版本：v0.6／100 人營區、打靶日與來電插曲  
日期：2026-11-08  
狀態：使用者已核可 Three.js、第三人稱斜俯視與走動探索方向，授權製作集合場、連辦公室及人物對話可玩雛形；另追加每日行程抽籤。完整一日遊戲仍依階段擴充。

## 1. 產品目標

製作繁體中文、可在電腦與手機瀏覽器操作的單人營區日常遊戲。玩家扮演連值星官，從早點名撐到晚間交接，在人數掌握、任務進度、弟兄士氣、個人精力與上下關係之間做決定。

風格為帶黑色幽默的生活模擬。笑點來自臨時加派、資訊落差、簿冊與現場不同步，以及角色各有立場。角色與單位均為虛構；遊戲流程為戲劇化設計，不作為現行軍事規定或勤務指導。

玩家體驗目標：一輪約 15–25 分鐘、每個選擇有可理解的代價、與值星班長的關係能實際改變後續事件，且結束後願意重玩不同處理方式。

## 3. 核心循環與時間

流程：查看任務 → 在營區走動探索 → 接近人物或互動物件 → 開啟對話框／檢查介面 → 決策或操作 → 顯示結果與數值變動 → 返回探索 → 完成節點後進入下一時段。既有 14 個節點為任務骨架，不強制每一步都以文字卡片切換。

開局先抽取當日行程。五種日型等機率抽取，結果保存於本輪存檔；完成抽取後不能重抽，重新開始新的一輪才會重置。雛形依日型改變在場／勤務人數、班長提醒、點名板依據及連長問話；完整行程先以預告表呈現，不代表所有時段已可玩。完整版本再依日型調整重點事件、任務需求與督導時機，維持各日型必要劇情可完成。

採遊戲內時間，玩家閱讀時不倒數。每個節點有預定時段與處理時間預算；選項可造成延誤。延誤累積至下一節點時觸發催促或準備不足，單次最高加重一級，避免早期失誤持續失控。

自由走動與查看紀錄不扣遊戲內時間；跨區移動在確認目的地時顯示固定分鐘成本，每次抵達只結算一次。對話、小遊戲及暫停時停止場景移動輸入。完成當前必要目標後，由玩家確認推進時段；支線是否略過需明示，不因站著閱讀而錯過事件。

## 4. 狀態與因果

| 狀態 | 範圍／初始值 | 用途 |
| --- | --- | --- |
| 紀律 | 0–100／65 | 集合秩序與執行穩定度 |
| 士氣 | 0–100／60 | 人員配合程度與集體情緒 |
| 精力 | 0–100／70 | 玩家處理額外事項的餘裕 |
| 連長信任 | 0–100／50 | 質問強度及結局評價 |
| 班長默契 | 0–100／50 | 是否主動補位、提供提醒與協助 |
| 延誤 | 0 分鐘起 | 時段超支與催促觸發 |

所有有上下限的數值變動後都須截斷至範圍內。重要結果另以旗標保存，例如「如實回報」「待查人員」「完成協調」「簿冊缺漏」，避免只以單一分數決定劇情。

班長默契 ≥70 時，特定事件開放協作選項；≤30 時，班長傾向按明確分工辦理，不主動補位。關係始終有修復機會。連長信任低於 30 時增加質問，但不能讓玩家無法完成一輪。

選項預覽顯示方向與成本，例如「花 10 分鐘／可能改善默契」；決策後顯示實際變動及原因。一般事件單項變動以 ±5–15 為初始平衡範圍，定稿後依試玩調整。

## 5. 操作玩法

### 5.1 人員清查：早點名與五查

使用 100 名虛構角色與可核對的名冊。角色狀態包括在場、報備外出、勤務中、待確認。玩家閱讀班長回報、報備紀錄與現場線索，標示異常並選擇查證方式。

檢查目標為「現場、名冊、回報是否一致」。應到及實到數由資料計算，不能寫死。提交前顯示未確認項目，可返回檢查；帶未確認事項提交會產生待辦與後續事件。不得以猜中單一人名作為唯一通關條件。

### 5.2 分配任務

三個班組、三類任務。以按鈕或下拉選單分派，拖曳僅作可選增強。各班組有負荷與可用狀態，各任務有人力需求與時限。系統即時提示重複占用及負荷超限，允許調整後送出。

妥善分工可增加準備度；一味把事情交給同一班會降低士氣與默契。不得出現無可行解的人力配置。

### 5.3 簿冊核對

並列「當日事實紀錄」與「待填簿冊」，要求修正 3–5 個欄位，例如時間、人數、處理結果。錯誤回饋須能指出依據。允許先查證再填，不要求玩家背誦先前畫面的數字。

如選擇未查證就簽，保留資訊不一致旗標，在連長質問與交接時回收。正確完成可減少追問，但會消耗時間或精力。

### 5.4 開庫取槍

沿用任務分配與簿冊核對介面，重點為人員協調、領用資料一致性及時程壓力。玩家檢視領用需求、相關角色到場狀態、虛構裝備清單與交接紀錄，可選擇先核對、請班長協助，或回報延誤並調整操課。

事件流程為「準備 → 核對 → 領用結果」，並建立當日歸還待辦。資料不一致時可查證或暫停該筆領用；未釐清項目保留異常旗標。晚間交接前須核對歸還狀態，使領用與歸還形成完整劇情。

以抽象管理流程呈現，不模擬實體庫房開啟方法、警戒配置或槍械操作。

### 5.5 督導官實施督導與點缺失

每輪必經督導事件，允許「無缺失」「一般缺失」「重大缺失」「兩類並存」四種結果。查核結果依玩家先前的現場、簿冊及任務狀態產生；隨機種子只決定查核重點，不憑空生成玩家無從預防的缺失。

| 分級 | 遊戲內例子 | 後果與改善 |
| --- | --- | --- |
| 一般缺失 | 非關鍵欄位漏填、工作完成卻未更新紀錄、環境整理未達事件要求 | 列管改善，消耗時間／精力，連長信任初始扣 5；可當場補正並申請複查 |
| 重大缺失 | 領用與歸還資料關鍵不一致且未處理、已知重要人員狀態不明卻回報無異常、未核對就宣稱完成重要交接 | 建立重大待辦，連長信任初始扣 15；暫停相關任務、查明並回報，完成改善與複查才可結案 |

以上為虛構劇本分級，不代表實際法規或正式缺失認定。一般缺失不因數量累積就自動改列重大，分級須由明確事件條件決定。歸還相關缺失只在已有歸還義務的查核時點判定，不得在尚未到歸還時間時算作缺失。

每項缺失顯示督導意見、現場證據、分級、改善方式、負責角色、期限及狀態。玩家可當場說明並改善、與班長分工補正，或先回報再調整原任務。提出異議須以既有紀錄供複核，不能只靠爭辯消除缺失。

處理流程為「列管 → 改善中 → 待複查 → 結案」。改善完成不自動結案，複查依證據判定。逾期另觸發催辦，但同一次查獲的基礎扣分只套用一次。督導結果會影響連長質問、班長關係及交接結局。

## 6. 事件與角色

主要角色：玩家、連長、值星班長、督導官、裝備管理承辦、行政承辦、其他幹部與三個班組。每位角色有明確訴求：準時、資料完整、人力足夠、保留休息或避免被追問。督導官依可見證據點缺失並要求改善；對話不只呈現單方面刁難。

至少 8 個插曲候選：臨時公差、集合前仍有人被留掃、名冊更新未同步、餐點需保留、器材未到、簿冊簽錯欄、其他幹部臨時改指示、班長提醒被忽略。每輪抽取 4 個，插入相容時段，不重複抽取。

示例事件「人到底歸誰叫？」：集合將至，另一名幹部要求外圍公差繼續整理。班長回報來不及。

| 選項 | 即時代價 | 後續影響 |
| --- | --- | --- |
| 主動聯繫雙方確認優先順序 | 消耗時間與精力 | 提升默契，取得明確回報依據 |
| 要班長照原時限帶回 | 集合較快 | 班長承受協調壓力，關係可能下降 |
| 先讓公差做完再集合 | 延誤 | 降低現場衝突，需向連長說明 |

對話可辛辣，但不使用真實姓名、羞辱特定群體或把不當對待設定為唯一有效玩法。

## 7. 結局與回顧

首版不因單一數值歸零立即結束；玩家均可到達交接。結局依下列優先順序判定，條件互斥處理由順序保證：

1. **交接還有一長串**：重大待查事項或重大缺失尚未結案，或未結事項達 3 件（包含未結案督導缺失；同一事項不重複計數）。
2. **孤軍奮戰的一天**：班長默契 ≤30 且精力 ≤30。
3. **連長記住你了**：連長信任 ≤30。
4. **神隊友值星組**：班長默契 ≥70、士氣 ≥60、重大未結事項為 0。
5. **穩穩交接**：紀律 ≥60、連長信任 ≥50、重大未結事項為 0。
6. **有驚無險**：其餘情形。

回顧畫面顯示結局、六項狀態、三個關鍵選擇、待辦清單及可改善方向。建議須對應玩家實際行為，不顯示未發生的事件。可重新遊玩或返回唯讀紀錄。

## 9. 畫面與互動

### 9.1 場景呈現方案

使用者已指定走動探索與人物對話框。建議以 Three.js 建立風格化、低多邊形營區，採第三人稱斜俯視跟隨鏡頭，讓玩家看得到自己、人物及互動位置。場景與角色先求可辨識，首版不追求寫實大世界。

| 方案 | 探索方式 | 素材與工作範圍 |
| --- | --- | --- |
| A：Three.js（建議主方案，待審） | 控制角色連續走動，靠近人物、門口或物件互動 | 營舍外觀、道路、簡化室內、角色模型、基本待機與走路動畫、碰撞區域 |
| B：照片場景（替代方案，待審） | 點擊出口切換照片視角，點人物或熱區探索；不宣稱可在照片內自由立體行走 | 已授權或自行製作的場景照片、人物立繪、出口及物件熱區 |

首版只製作核可的一種場景模式，不同時承諾兩套。事件與對話資料共用，未來可替換呈現方式。若採照片，須另確認素材來源；不得直接挪用 PTT 照片。Three.js 方案可搭配人物立繪，但不把照片自動轉為可自由行走的 3D 場景。

### 9.2 地點與探索內容

| 地點 | 主要人物／物件 | 對應玩法 |
| --- | --- | --- |
| 連集合場 | 值星班長、三班人員、集合看板 | 早晚點名、任務分配、五查 |
| 連辦公室／會議區 | 連長、行政承辦、課表與簿冊 | 課前會議、寫簿工、被連長電 |
| 裝備領用區 | 裝備管理承辦、領用表、交接點 | 開庫取槍情境、資料核對與歸還 |
| 餐廳外與公差區 | 帶隊班長、留餐紀錄、整理點 | 用餐、公差與集合衝突 |
| 營舍走廊／值星交接點 | 值星班長、公告、交接桌 | 支線對話、關係修復與交接 |

督導官依時段出現在指定查核點，透過對話宣布查核結果，再開啟缺失清單。各區以短道路或門口轉場相連，首版不製作完整真實營區配置。必要任務有地點指引與可開關的互動提示，避免玩家只因找不到人物而卡關。

### 9.3 操作與人物對話框

桌面以 WASD／方向鍵移動、E 或 Enter 互動、Esc 關閉可退出的視窗；手機以虛擬方向控制與互動按鈕操作。採照片方案時，改為點擊熱區與出口，並保留鍵盤焦點操作。

靠近可互動目標時顯示名稱與操作提示，同時只選定一個目標；有多個目標時可切換。阻擋穿牆、穿越物件及走出地圖，提供「返回安全位置」。

人物說話使用畫面下方的 HTML 對話框，包含姓名／職務、表情立繪、台詞及選項。對話可逐字顯示，點擊先顯示整句，再點擊才進下一句；設定可關閉逐字效果。選項以明確按鈕呈現，選定後顯示角色回應與數值變化。首版不含配音或自由輸入聊天。

一般對話可關閉並稍後繼續；必要決策不能透過關閉視窗略過。開啟對話時鎖住角色移動及背景互動，關閉後恢復焦點。已提交的選擇不能因重新點擊人物而重複領取效果。NPC 依時段與事件狀態更換台詞，無新事件時提供簡短日常回應。

### 9.4 介面配置

介面沿用軍綠、米色紙張、橘紅提醒色與簿冊意象。優先確保文字好讀，避免整頁迷彩與過多裝飾。

畫面包含：開始頁／簡短教學／主遊戲／人員清查／任務分配／簿冊核對／當日紀錄／結局／來源與設定。

主遊戲以場景為主要畫面，上方顯示時間與精簡狀態，角落顯示目前目標及地點導引，下方於互動時顯示人物對話框。待辦、完整狀態與當日紀錄可展開。清查、分工及簿冊以覆蓋面板開啟。手機版縮減常駐資訊，控制區與對話選項不得互相遮擋。每次選擇先呈現結果，再由玩家按下一步，避免錯過回饋。

支援 Tab、Enter、明確焦點提示，點擊範圍至少 44px。狀態不能只靠顏色區分。尊重減少動態效果設定；首版不自動播放音效。重新開始須確認，避免誤清進度。

## 10. 工程方案

建議使用 Vite、TypeScript、Three.js 與 HTML／CSS 介面，建置為靜態網站。Three.js 負責場景、鏡頭、角色及互動目標，HTML 負責對話框、任務與表單。若核可照片方案，替換為照片熱區呈現層，其餘規則共用。無後端、無外部 API、無付費依賴；事件資料與規則分離。套件版本於實作時依官方文件確認並鎖定，這份文件不指定未查證的版本或 API。

建議模組：

- `engine`：狀態更新、條件判斷、節點推進、結局判定。
- `events`：事件文案、選項、條件、效果、來源。
- `roster`：人員與人數計算、狀態一致性。
- `tasks`：任務配置及衝突檢查。
- `storage`：存讀檔、版本檢查與錯誤恢復。
- `ui`：畫面呈現、操作與無障礙回饋。
- `world`：區域載入、角色位置、鏡頭、碰撞與安全位置復原。
- `interaction`：附近目標判定、互動條件、任務觸發與單次執行保護。
- `dialogue`：台詞節點、表情、分支、閱讀進度與對話框焦點。
- `assets`：模型／圖片載入、來源授權紀錄、失敗佔位與資源釋放。

場景資料包含 locationId、spawnPoints、walkableAreas、obstacles、exits、npcSpawns、interactables。互動物件包含 id、label、type、position、availability、eventId。對話節點包含 id、speakerId、portraitExpression、text、choices、next、conditions。世界呈現只送出互動意圖，由事件引擎判斷與更新遊戲狀態，不能在畫面更新迴圈中加減分。

存檔另保存 locationId、playerPosition、playerFacing、activeInteractionId、dialogueNodeId、visitedLocations、discoveredClues。位置只在有效可行走區域恢復，無效時回到該區安全出生點；對話未提交選項時可恢復原句，已提交則恢復結果，不能重複套用。區域切換、對話節點與重要互動完成時自動存檔。

3D 場景先使用靜態碰撞形狀及明確互動區，不引入完整物理模擬。提供低畫質模式，降低陰影、解析度與裝飾物。分區載入，離區釋放不再使用的資源。WebGL 不可用或渲染失敗時顯示說明並提供「地點清單＋人物／物件按鈕」的簡化探索介面，沿用相同任務條件與移動時間，仍可完成主流程。

核心狀態：schemaVersion、runId、seed、phaseIndex、eventQueue、stats、flags、roster、assignments、pendingIssues、equipmentLedger、inspectionFindings、history、updatedAt。隨機種子及已抽事件寫入存檔，重新整理不能重抽結果。

equipmentLedger 保存虛構裝備領用、待歸還與核對狀態。inspectionFindings 每筆包含 id、sourceEventId、severity（general／major）、evidenceRefs、owner、deadlinePhase、status、correctiveAction、recheckResult、penaltyApplied。與 pendingIssues 以同一 id 關聯，防止重複列管與扣分。分級條件為明確資料規則；讀檔須保留改善、複查與扣分狀態。

事件資料：id、phase、title、body、conditions、choices、sourceRefs。選項資料：id、label、costHint、requirements、effects、resultText、next。效果僅允許預定義操作，禁止執行文案中的程式碼。

選擇處理順序：檢查條件 → 防止重複送出 → 計算完整新狀態 → 套用數值上下限 → 紀錄結果 → 儲存 → 呈現。結果畫面與下一步狀態一併存檔，重新整理不可重複加減分。

使用 localStorage，於完成決策及小遊戲提交後自動保存。讀檔需驗證結構與版本；資料毀損時提示可重新開始，不使頁面空白。瀏覽器阻擋儲存時改為本次記憶體遊玩並明示無法保存。首版不收集分析資料或個資。
